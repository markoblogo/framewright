# Learn from video corrections

Use owner feedback to prevent the same avoidable correction in another film.
This is a Framewright agent-led procedure using the existing brief, case records
and revision journal. It is not a background learner, automatic vision grader or
an installed slash command. No external skill code is copied or required.

## Where the knowledge lives

In this studio, current owner preferences live in [video taste](../../../docs/video-taste.md).
Another project should use its own existing preference document; do not inherit
this studio's voices, colours or branding as generic Framewright defaults. Keep
the source correction and exact-version decision in the owning production record.
The preference document is a compact index of reusable lessons, not another journal.

## Before proposing or rendering

Read only preferences relevant to the selected production, including their scope
and exceptions. Link the chosen IDs in the existing private brief/scene plan:

| Rule | Application in this film | Evidence to inspect before handoff | Status |
| --- | --- | --- | --- |
| Applicable rule ID | Concrete scene/layer or explicit exclusion | Named encoded excerpt, reduced preview, listening or source comparison | planned / blocked / verified |

Do not fill the brief with unrelated rules or create a second state database.
Carry applicable checks into the existing handoff/revision record. Use the existing handoff states: unperformed is planned; a named missing input,
authority or needed correction is blocked; verified names an actual observation.
A pilot checks only what it actually contains: plan the remaining duration and inspect the full
film's relevant scenes before claiming they comply. Inspect both final formats
when both were requested, including a delivered centre crop if that route was selected.

For an explicitly agreed autonomous trial, use the already selected briefing and
review contract: do not insert new intermediate owner approvals. Keep internal
checks/self-corrections within scope; capture final feedback after complete delivery.
Unresolved resource/access gaps use the trial's agreed fallback or blocked outcome.

## Capture a correction

At an owner correction, retain their words, the affected version/scene, requested
change, protected elements and later decision using the existing revision flow.
At acceptance or closeout, ask of that evidence:

- Is this a reusable preference, an explicit standing instruction, a case-only
  choice, or a functional defect/brief misunderstanding? Keep bugs and case-only
  details in their owning records; they need not become taste rules.
- Is the same lesson already present? Link or improve that rule's application/check
  instead of adding a paraphrase. A repeated failure is evidence the work loop
  missed the rule, not permission to invent a stricter aesthetic or numeric threshold.
- What is the narrowest useful scope: this series, narrative explainers, character
  scenes, voice-led tours, small-screen text, or a genuine owner-wide instruction?
  Repetition in unrelated cases supports reuse; a single explicit standing choice
  can also be recorded. Do not universalise the exact pixel width of one repair.
- What reason did the owner give? Preserve it. If none was supplied, write
  **reason not recorded**. An operator explanation may be marked inferred but
  cannot silently become the owner's rationale or a wider constraint.

Retain a rule's stable ID, current wording, scope/exceptions, source case/quote,
reason provenance and a concrete check. For example, the Pantheon correction
supports reduced-size line inspection; it does not require every film to use blue
8 px lines. Preserve the superseded design and failed attempts in the source case,
not as competing current instructions in the preference index.

## Decide what is already authorised

An explicit correction or standing instruction already given by the owner can be
recorded at its stated scope without asking them to approve the same decision again.
Use a broader or inferred rule only as a labelled proposal until the owner selects
it. If a new explicit project brief is an exception to an older default, record that
exception and follow the current instruction. Ask only if an actual unresolved
conflict changes the result; a different genre alone is not a conflict to escalate.
Do not replace an accepted master or reopen paused productions to apply new defaults.

## Check before showing the next result

Apply the selected rules before the owner reviews the candidate. Retain the file,
range/viewing size and verifier or observation that supports each checked item.
A successful render, checklist tick or still cannot establish sustained motion,
natural voice, accurate tracking or readable animation. Leave unperformed checks
as planned (or blocked with the actual reason), correct observed violations within
the authorised scope, and keep
owner creative/listening acceptance separate from operator inspection.
Use existing deterministic checks for properties they really measure; do not call
a text matcher or duration test a creative-quality detector. Do not fabricate pass
results, invent new thresholds or start a generator merely to satisfy this procedure.

After a further correction, link it to the existing rule and note which application
or check failed. Update that step so the lesson affects the next production.
No fixed count of rules, cuts, movements or review rounds is imposed on every film.

## Reading past sessions

Use the current conversation and relevant retained case evidence first. Read earlier
sessions only when requested and accessible within the authorised project scope;
state which sources were actually read. A quoted example asking for three sessions
is not evidence that three sessions were analysed. Never invent missing dialogue,
a silent user edit or approval. Keep manuscripts, customer material and transcripts
private; a useful sanitised lesson can cite the case without uploading raw history.
Do not update global agent memory, install third-party skills, change schedules,
publish, commit/push or release as a side effect of learning from feedback.
