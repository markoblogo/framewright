# A readable motion specification in the existing production

Use `MOTION.md` as the human/agent creative entry for a reusable film or a scene with
meaningful timing, action or cross-scene state. It supplements the existing producer
brief and editable recipe; it is not another journal, runtime or universal importer.
A simple correction can stay in its current revision request instead of gaining a file.

Adapted concepts: OpenMotion [Motion.md](https://github.com/nexu-io/openmotion/blob/fcbaa2b0296167b0f14f47aa6c414f5bdd41316f/docs/motion-md.md),
[director](https://github.com/nexu-io/openmotion/blob/fcbaa2b0296167b0f14f47aa6c414f5bdd41316f/skills/openmotion-director/SKILL.md)
and [review](https://github.com/nexu-io/openmotion/blob/fcbaa2b0296167b0f14f47aa6c414f5bdd41316f/skills/openmotion-production/references/review.md).
These are explicit reviewed references, not installed global instructions or claims of
Framewright runtime compatibility. OpenMotion source is Apache-2.0; its media/fonts
and examples retain their individual terms. No upstream implementation is bundled here.

## One entry, existing sources

Keep the file beside the private source project. Link the existing brand profile or
DESIGN.md, selected recipe, source/claims and timing file. Do not maintain a competing
palette, copy approvals or make another project/status database. Current exact-version
choices, waits and evidence continue to come from `project.py brief PROJECT.json`.
Use [accepted-film templates](templates.md) for actual reuse and content bounds.

Write only the relevant decisions:

| Part | Decision to retain |
| --- | --- |
| Intent and source | What the viewer should understand/feel; facts versus illustration; actual sources |
| Picture and sound | What visibly/audibly develops and why it serves that intent |
| Time and state | Timing source, object identity, event order, meaningful holds and handoff to the next scene |
| Keep and replace | Protected properties, editable material, longer copy/missing-input handling, requested aspects |
| Runtime and material | Actual editable implementation, exact tool versions, local assets, permissions and execution limits |
| Review and delivery | Named defect/risk, relevant time window, expected visible result, exact outputs and remaining decisions |

A [filled structural example](../../../examples/production-reuse/MOTION.md) illustrates
the format without claiming a rendered or accepted film. The field order is not a shot
order. No fixed shot count, effect quota, duration, palette, numerical motion score or
universal subject-size threshold follows from the example.

## Direct movement rather than filling a template

Before rendering, describe the important change and its viewing payoff. “The card
slides in” identifies a presentation method; explain what the viewer discovers or
experiences. Moving a subject is necessary for some briefs but does not establish
interesting acting, readable structure or good pacing. A quiet hold may be intentional.

Select the smallest representative motion pilot of the actual risk, including its
entry/result context. Before finishing a multi-part film, inspect a low-cost full-duration
moving draft: a good opening does not qualify the middle. Repetition is appropriate when
it serves explanation or a selected series; otherwise vary emphasis, framing and timing
for content reasons, not random novelty. Do not demote a missing key action to a still.

Where continuity matters, retain the latest object and time state across scenes. For a
manipulation, distinguish attachment from environmental support: a hand can correctly
hold a cup while its release point lies outside the table. Check the footprint as well
as the attachment. Keep annotation regions separate from the scene geometry in each
aspect; a numeric rig check cannot establish readable captions. The retained
[Praxis correction](../../../docs/productions/praxis-robot-engineering.md) is an example.

## Adapt, correct and prove at the requested scope

Use one timing source for dependent picture/audio events; keep source time separate
from output time when recutting. Absolute-time/reseek checks apply where supported by
the actual runtime; they do not certify artistic quality or sound. On a real correction,
record interval, defect, desired change and protected properties in the existing
[revision contract](revisions.md); inspect neighbouring context and the exact candidate.
A new film or aspect does not inherit the earlier owner's acceptance.

Review separately: information/intent, visual appeal, motion/pacing, spatial continuity,
readability and sound. Record actual encoded viewing/listening coverage; frame sheets,
meters and mathematical assertions cannot stand in for full-speed viewing or listening.
A repeated failure should change staging, shared state, material choice or review
coverage; adding another synonymous rule alone is not a demonstrated repair.

For portable reuse, include owned/cleared source, required local assets and notices,
replaceable inputs, a preview and exact-version evidence. Reuse existing hashes and
package tools. An optional OpenMotion Motion Package may wrap that distribution; its
manifest is an inventory, not a second production journal. Its checker does not prove
Markdown links, licence clearance, rendered quality or arbitrary engine compatibility.
Do not silently refresh unexplained hashes or install a runtime from a linked document.
